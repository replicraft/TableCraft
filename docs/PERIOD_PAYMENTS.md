# Period counts and payment components

`NPer`, `IPmt` and `PPmt` extend the shared [financial function profile](FINANCIAL_FUNCTIONS.md).
They return Double, use the existing numeric/Boolean-to-Double conversion kernel,
reject explicit NULL/nonnumeric/non-finite carriers, and require timing exactly
0 or 1. Source-free evaluation and bound retrieval share function-specific optional
argument normalization. Supplied expressions evaluate eagerly in written order;
omitted optional slots default to zero, independently of explicit NULL.

| Function | Required arguments | Optional arguments, default zero |
| --- | --- | --- |
| NPer | Period rate, payment, present balance | Future balance, timing |
| IPmt | Period rate, selected period, total periods, present balance | Future balance, timing |
| PPmt | Period rate, selected period, total periods, present balance | Future balance, timing |

Microsoft documents Double results and selected payment periods from 1 through
the total period count. Its examples use consistent rate/payment units and signed
cashflows. References: [NPer](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/nper-function),
[IPmt](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/ipmt-function),
[PPmt](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/ppmt-function).

```sh
tablecraft query eval "SELECT NPer(.01,-100,1000) AS Periods"
tablecraft query run "SELECT IPmt(.01,1,12,1000) AS Interest,PPmt(.01,1,12,1000) AS Principal"
```

## Implemented calculations

NPer solves the positive-base real annuity equation. Zero rates use the linear
cashflow equation. Nonzero rates use normalized balances and log1p-based relative
ratios, with a factored near-zero limit and separate-log fallback when forming a
ratio would overflow or round to a nonpositive value. Rates at or below -1,
nonpositive logarithm ratios, interest-only/no-unique-solution cases and all-zero
cashflows return Domain. A nonzero-balance zero-rate equation with zero payments
returns DivisionByZero. Non-finite intermediate/result values return Overflow.
The function does not invent a period count for an unsolvable or ambiguous target.

IPmt and PPmt validate `1 <= per <= nper`, derive the periodic payment from the
shared annuity kernel and calculate one component with constant work. IPmt returns
zero for zero rates and for period one of beginning-of-period payments. Otherwise
it calculates signed accrued interest; PPmt subtracts that interest from the fixed
payment. Positive-rate periods after the first use discounted remaining payments,
avoiding cancellation between large accumulated balances late in a schedule.
Other cases retain the forward real-power calculation. No amortization schedule
is allocated or scanned by the production kernel.

The APIs support three-to-five arguments for NPer and four-to-six for IPmt/PPmt.
Both SQL paths retain the required/optional positions, including supplied sixth
arguments with omitted future balances. Bound arguments retain ordinary pruning,
grouping, correlation, aggregate, domain and collection-item scope handling.
Cancellation/work limits and buffered failure behavior remain unchanged.

## Evidence and remaining work

Two new generated properties each use 256 fixed-seed cases: NPer recovers
identifiable, well-conditioned schedules generated by a separate period ledger;
IPmt/PPmt agree with independently stepped accrual balances and preserve payment
identity. The NPer inversion property excludes numerically ill-conditioned
interest-only neighborhoods; explicit ambiguity controls verify Domain rather
than treating those exclusions as compatibility evidence. Boundary controls cover
zero/near-zero/subnormal rates, first/last/beginning periods, invalid ranges,
non-finite/NULL/type errors, required/optional slots and eager failures. A new bound
query control covers six-argument retention, aggregate/domain/correlated composition
and late errors. The prior annuity property now also uses 256 fixed-seed cases.

[SavedPaymentFixture](testing/SavedPaymentFixture.java) adds ten original inert
queries over the existing financial recipe. Its
[comparison runner](testing/compare_payment_functions.py) passes 306 controls
using 400-digit Decimal period-by-period ledgers, scalar and bound evaluation,
raw native metadata/row getters, rendered SQL and direct/saved/named execution.
Four fresh Jet 4/ACE 2007/V2016/V2019 files retain their hashes. Cases include end/
beginning schedules, root parameters, grouping, derived reads, UNION, crosstabs,
unsolvable targets and buffered refusal paths. The first independent run exposed
late-period cancellation; the corrected discounted path passes the original
2e-13 relative comparison tolerance without loosening it. Jackcess does not execute
these queries or formulas.

Finite Double rounding, ill-conditioned inversion and extreme intermediate
range/cancellation remain limitations. Selected/total periods use finite Double
without implicit Integer rounding; native fractional/negative-period coercion,
subtypes, NULL/timing/error order and precision remain unqualified. In particular,
Microsoft's PPmt parameter documentation uses Integer spellings while IPmt uses
Double; the current shared carrier profile does not establish native equivalence
for that distinction. Other financial functions remain separately tracked.
Windows Access comparison remains deferred, not a blocker or completed evidence.
