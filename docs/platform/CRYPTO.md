# Checked cryptographic integration

`tablecraft-crypto` owns the cryptographic operations already used by ACE's Agile,
legacy, root-mask and SID consumers. It has no engine, adapter, SQL, filesystem,
I/O or host dependency. The existing workspace algorithm versions and zeroization
features are retained; the extraction adds no cipher, native encryption profile
or signature-verification capability.

The working API provides:

- Fixed zeroizing MD5/SHA-1/SHA-256/SHA-384/SHA-512 digests over borrowed parts.
  The output is 64 bytes with a zero tail after shorter digests.
- Checked AES-128/192/256 ECB and CBC operations with no padding. CBC requires an
  explicit 16-byte IV. Unsupported key lengths and incomplete blocks return
  payload-free `CryptoError` variants before input mutation.
- `Rc4Stream`, whose position persists across supplied segments. It has no
  Debug/Clone/serialization implementation. Its underlying state is zeroized on
  drop through the existing workspace dependency feature.
- Content-constant-time equality through the existing `subtle` implementation;
  lengths are checked separately and are not hidden by this contract.

These are prepaid primitives. They allocate no variable-sized scratch buffers,
choose no implicit limits and invoke no callbacks. The caller must bound input
sizes, charge resource/work pools and check cancellation around each bounded
operation. The API does not make arbitrary input lengths free or cancellable.
Owned digest output/finalization bytes and upstream cipher states use the
existing zeroization facilities; borrowed input/key lifetime remains caller-owned.

## Native policy stays in ACE

ACE retains its public native API and sanitized inspection errors. Its adapters
map primitive failures at the existing native boundary. Password presence/length,
UTF-16 encoding, spin counts, native salt/block-key derivation, verifier padding,
encoding-key IV folding, page geometry and source bounds stay in the engine.
Header-mask ranges/keys, selected SID columns, remasking, native descriptors and
preservation/rewrite orchestration also stay there.

The legacy native ECB consumer intentionally transforms only complete blocks and
preserves its trailing bytes. That native tail policy remains in ACE; the generic
AES operation rejects partial blocks. Legacy RC4 verifier and hash processing
share one stream, rather than restarting it at the second segment. The legacy
32-byte padded key buffer also remains native policy, while Agile retains its
native hash-algorithm enum and maps it explicitly to the shared primitive.

Existing ACE byte/step charges, cancellation checkpoints and scratch-first atomic
publication ordering are unchanged. The platform layer does not create a second
budget or publish a partially transformed native page. ACE retains `zeroize` for
its own password, key, page and collation buffers. Independent fixture encoders
and digest goldens retain direct dev-only AES/CBC/SHA-2 dependencies, so their
expected bytes are not generated by the extracted wrapper.

This does not verify file authenticity, HMACs or digital signatures, establish
trust, or widen native encrypted read/write qualification. See
[native encryption](../access/storage/NATIVE_ENCRYPTION.md) for the owning native
profiles and limitations.

## Verification

The first platform compile/runtime run passes four independent functions covering
standard `abc` digest answers and zero tails, NIST SP800-38A ECB/CBC vectors at all
three AES key widths, multi-block CBC and segmented RC4 continuity, and exact
geometry/equality controls. The unchanged ACE tests pass 19 encryption unit
functions, three SID patch functions and ten source/page/rewrite integration
functions, including cumulative budgets, cancellation, credentials, preservation
and publication failures. These are 36 distinct runtime functions, four new.
No native Microsoft Access or new JVM fixture execution was performed for this
extraction, and existing vector/helper source bytes were retained.
