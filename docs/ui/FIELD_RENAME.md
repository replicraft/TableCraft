# Reviewed saved-field names

The shared Datasheet heading and Table Design name cell now use one bounded
local proposal editor. Double-click the name, or choose **Rename Field** from
its context menu, then explicitly Save or press Ctrl+S. Enter and focus loss do
not save. The original displayed schema stays unchanged until the consuming
runtime save and checked replacement publication complete. The entry command remains disabled without supported host/direct-native metadata.
An unsupported source inspection keeps the proposal read-only and cannot Save.

The normal desktop workflow passes headless native save/reopen, unchanged review,
Design selection, duplicate refusal, exact dirty-close and retained sort retry
checks. The [coordinated record](../../tests/results/schema/field-workbench-workflows-2026-11-09.json)
retains earlier failures and corrections without adding repeated coverage.
Source-free rendering has separate evidence below.

## Identity and supported proposals

A target binds the exact open tab/document revision, true stored field name and
actual native column number. Captions and rendered positions supply no identity.
The runtime inspects the original source without a proposed name, AFTER image,
write lease or save capability. Only positive source facts permit editing;
unsupported or interrupted checks remain visible and may be retried explicitly.

Current native support is the [empty ACE16 explicit-OFF profile](../access/writes/FIELD_RENAME.md):
a non-key ordinary Number Long with stored Required(false)/zero default, or
compressed Short Text255 with stored Required(false)/AllowZeroLength(true) and
no default. Original and proposed names are ASCII. A positively inspected fitted
source allows growth/shrink within existing native capacity; an older same-width
observation still requires its exact original width. The native identifier ceiling
and duplicate rules still apply. A larger proposal can still refuse during the
consuming review when either physical owner lacks space. A non-ASCII
sibling, generated ID, populated table, unsupported declaration or unknown source
refuses. These are TableCraft's current qualification limits, not general Access
name restrictions. A bounded unsupported proposal remains visible without
acquiring save authority.

The shared `tablecraft-builders::table::field_rename::FieldRenameNameProfile`
keeps the observed original width and supported name shape explicit. UI rejects
inconsistent facts, empty/non-ASCII proposals and stale identities; it never
converts a displayed capability into native authority. Sectioned Fluent catalogs
provide distinct same-width and fitted guidance in all eight interface languages.

## Save, close and checked publication

The typed review binds the exact proposal revision, original identity and new
spelling. The host compares the review and opaque capability before starting the
nonreplaceable SaveWorker. Cancellation/refusal preserves the proposed text and
actual retained native resource owners. Exact no-op spelling still receives a
real review, then consumes only its readonly complete-image witness: there is no
native save ID, journal or changed-save receipt. Case-only changes remain actual
changed saves when qualified.

An untouched editor closes without a dirty prompt; the host revokes only its
recorded readonly inspection. Dirty proposals use exact-revision
Save/Discard/Cancel and retain the requested tab/file/window transition through
review or original/no-write refusal. A stale choice cannot discard newer text.
Save resumes the transition only after the actual known-replacement ACK and
successful full-image witness read. Confirmation itself supplies no native
permission and does not mutate a file.

A dedicated rename publication consumer uses the existing neutral replacement
graph owner. It preserves tab IDs/order, preferences and source-free scratch SQL
bytes while invalidating old native rows/results/handles. In Design, selection
follows the accepted native field number and exact new name only after fresh
schema validation; a stale row position is not restored. Scratch text is never
rewritten to the new field spelling. Filter/sort definitions remain opaque and
must pass fresh revalidation; a failed restoration retains the original intent
and reports an error rather than silently dropping it.

If the accepted replacement cannot be verified, Retry or Return retains the
exact proposed name, outcome and cleanup history. Return exposes a readonly name
editor with stale-source mutation guards until an explicit fresh document open.
Closing that presentation does not erase the retained warning or undo a write.
Unchanged-review failures use explicit no-change/read wording and never claim
Saved or native cleanup. Later rename/ADD authority is not inferred from the
successful first rename; the native source-history limits remain separate.

## Presentation evidence

The actual retained Windows Access Datasheet (1920×1141) and Table Design
(1920×1152) images were opened directly. Both were captured in VirtualBox; OS
scale is unrecorded. There is no retained expanded Rename Field menu, inline
rename editor, close confirmation or error/status capture. Those surfaces are
uncaptured adaptations. The complete Ribbon and separate filter/sort chevron
remain present. Eight dedicated sectioned Fluent catalogs own the new messages.

Source-free offscreen modes cover name, unsupported width, source refusal,
unchanged spelling, pending review, close confirmation and changed/unchanged
Return. Their illustrative state owns no native capability, actor, file or
journal. The corrected reserved status-panel matrix rendered all 22 cases on
macOS 14.7.2 arm64: eight English light and eight English dark at 1280×820/1×;
three German at 1100×760/1.25× and three Japanese at 1100×760/1×. All 22 images
have been directly reviewed without clipping; compact German/
Japanese layouts retain the complete Ribbon through its existing horizontal
overflow behavior. These renders establish neither native writes nor Windows/Access
interaction, dependency repair or pixel parity. Final functional/visual acceptance
must be reported separately rather than inferred from these source-free scenes.
