# Reviewed saved-field names

The shared Datasheet heading and Table Design name cell now use one bounded
local proposal editor. Double-click the name, or choose **Rename Field** from
its context menu, then explicitly Save or press Ctrl+S. Enter and focus loss do
not save. The original displayed schema stays unchanged until the consuming
runtime save and checked replacement publication complete. The entry command remains disabled without supported host/direct-native metadata.
An unsupported source inspection keeps the proposal read-only and cannot Save.

The normal desktop workflow passes headless native save/reopen, unchanged review,
Design selection, duplicate refusal, exact dirty-close and retained sort retry
checks. The [coordinated record](../../tests/results/schema/field-workbench-workflows-2026-11-09.json)
retains earlier failures and corrections without adding repeated coverage.
Source-free rendering has separate evidence below.

## Identity and supported proposals

A target binds the exact open tab/document revision, true stored field name and
actual native column number. Captions and rendered positions supply no identity.
The runtime inspects the original source without a proposed name, AFTER image,
write lease or save capability. Only positive source facts permit editing;
unsupported or interrupted checks remain visible and may be retried explicitly.

Normal desktop inspection and review now use the separate
[current-metadata profile4](../access/writes/FIELD_RENAME.md). The target remains
a qualified non-key Number Long or compressed Short Text255 declaration; original
and proposed names are ASCII. The unencoded ACE16/subversion-zero eleven-page
source must prove its actual single-user-table roles, explicit Name AutoCorrect
OFF, ordinary row/index/constraint and NoRequired evidence, safe dependencies and
exclusive property ownership. Missing settings never imply OFF. NameMap,
expression/calculated dependencies, nonempty validation and nonliteral defaults
remain refusal conditions.

That proof observes the actual current image rather than reconstructing how it
was created. Empty rows, populated rows, prior name changes, retained counters and
tombstones all enter the same proof; none independently supplies rename
authority. Fitting growth/shrink, equal widths, case-only changes and unchanged
spelling share this family. Existing parser-bound definition/property capacity,
identifier and duplicate checks still apply, so a shape-valid proposal may refuse
during consuming review. Unknown roles, unsupported declarations, generated IDs,
other layouts and native programs do not become qualified merely because an
earlier operation succeeded.

The original empty same-width/fitted profiles and dense populated Number replay
profile remain separate native/recovery languages. The normal runtime neither
selects them by row count nor retries them after a current-source refusal. An
older same-width presentation observation still requires its exact width. These
are TableCraft qualification limits, not general Access name restrictions.

The shared `tablecraft-builders::table::field_rename::FieldRenameNameProfile`
keeps the observed original width and supported name shape explicit. UI rejects
inconsistent facts, empty/non-ASCII proposals and stale identities; it never
converts a displayed capability into native authority. Sectioned Fluent catalogs
provide distinct same-width and fitted guidance in all eight interface languages.

## Save, close and checked publication

The typed review binds the exact proposal revision, original identity and new
spelling. The host compares the review and opaque capability before starting the
nonreplaceable SaveWorker. Cancellation/refusal preserves the proposed text and
actual retained native resource owners. Exact no-op spelling still receives a
real review, then consumes only its readonly complete-image witness: there is no
native save ID, journal or changed-save receipt. Case-only changes remain actual
changed saves when qualified. For both empty and qualified populated sources,
the retained unchanged-review owner blocks conflicting edits until its checked
read-only reopen completes; it never becomes a native save actor.

Normal-host populated cases preserve actual rows containing a positive Number,
NULL and a negative Number through growth, shrink and equal-width changes. They
compare complete independently authored replacement bytes, then open the saved
file in a separate desktop host and check the actual fields and records again.
The generated counter and index bytes remain part of that complete-image proof.
The populated workflow also continues through a real row edit (ID1: 42→99),
an omitted-field insertion (generated ID4 and stored Number default0), deletion
of the ID2 NULL row and a separate host reopen. Both growing and shrinking names
retain IDs1/3/4 and values99/-7/0; each write compares the complete independent
image, including inactive records/keys and generation history. MCP exercises the
same row services from a fresh renamed-file session. The shared insertion widget
helper retains the original empty-table checks while allowing populated journeys.
These are earlier populated-profile observations, not evidence for every current
metadata source. The new current-profile regressions require repeated
grow/shrink/regrow saves and another rename after that row deletion, with exact
independent images and fresh reopening. These now pass in the complete desktop
and MCP unit batches. Native controls additionally preserve opaque free bytes,
nonzero NULL backing and the inactive catalog capacity of the existing inline
Number/Short Text source. Schema-purpose certificates cannot authorize ordinary
row writes. Populated Short Text or arbitrary imported databases cannot be
inferred from the Number journey.
This is headless workflow evidence, not Windows/Access rename-save qualification
or admission for every populated database.

An untouched editor closes without a dirty prompt; the host revokes only its
recorded readonly inspection. Dirty proposals use exact-revision
Save/Discard/Cancel and retain the requested tab/file/window transition through
review or original/no-write refusal. A stale choice cannot discard newer text.
Save resumes the transition only after the actual known-replacement ACK and
successful full-image witness read. Confirmation itself supplies no native
permission and does not mutate a file.

A dedicated rename publication consumer uses the existing neutral replacement
graph owner. It preserves tab IDs/order, preferences and source-free scratch SQL
bytes while invalidating old native rows/results/handles. In Design, selection
follows the accepted native field number and exact new name only after fresh
schema validation; a stale row position is not restored. Scratch text is never
rewritten to the new field spelling. Filter/sort definitions remain opaque and
must pass fresh revalidation; a failed restoration retains the original intent
and reports an error rather than silently dropping it.

If the accepted replacement cannot be verified, Retry or Return retains the
exact proposed name, outcome and cleanup history. Return exposes a readonly name
editor with stale-source mutation guards until an explicit fresh document open.
Closing that presentation does not erase the retained warning or undo a write.
Unchanged-review failures use explicit no-change/read wording and never claim
Saved or native cleanup. Later rename/ADD authority is not inferred from the
successful first rename; the native source-history limits remain separate.

## Physical capacity and correction

The fitted shape observation is not a promise that every 64-unit ASCII name fits.
A normal-host headless case uses a genuinely near-full admitted history: a
29-character name receives a consuming native capacity refusal, remains editable
and starts no save worker or journal. Editing that same proposal to 28 characters
creates a newer revision and saves only through a fresh review and complete-image
witness. The final field retains its native number and tab identity.

Subsequent row edits require independent qualification after this schema save.
The [retained-tail row proof](../access/writes/RETAINED_DEFINITION_TAILS.md) now
supports the demonstrated insertion/update/deletion journey while preserving
newly free historical TDEF bytes. Every later rename must freshly qualify its
current source; ADD retains its separate admission and cannot inherit authority.
