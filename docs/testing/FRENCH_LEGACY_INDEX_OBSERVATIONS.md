# French Legacy stored-index oracle

The [compact oracle receipt](results/french-legacy-index-oracle-2026-10-26.json)
records actual ACE16 V2016/V2019 originals with French descriptor `1036/0/0`
and matched General Legacy `1033/0/0`. Both profiles passed descriptor, complete
key/reference and cursor-order checks: 456 logical memberships, or 304 physical
entries after deduplicating the Asc/Twin aliases. No engine implementation or
native Access comparison is established by this oracle preparation.

## Exact evidence

[FrenchLegacyIndexFixture.java](FrenchLegacyIndexFixture.java) is original
repository-owned code using the reviewed Jackcess 5.0.4 JAR, SHA-256
`19a7494a56f439a57fda85c059b019b665802085cec5ae8186d1e028cc1bdfbc`.
Its existing dependency/license provenance is in [the fixture ledger](FIXTURES.md).
Public `ColumnBuilder.setTextSortOrder` receives an explicit
`ColumnImpl.SortOrder(lcid, variant, version)`. Neither headers nor descriptors
are patched. Expressions are disabled, UTC is explicit and linked opens throw.

Each original has French and GeneralLegacy tables with identical 38 ID/Text rows.
Nonunique Asc/Twin declarations share physical index zero; Desc uses physical
index one. All actual indexes have one owned root leaf. Read-only reopens retain
actual field descriptors, locations, every encoded key and row reference, and
complete cursor order. A separate Python raw-page decoder reconstructs physical
prefix-compressed keys and verifies their bytes/references against the getters.
Original hashes are checked before and after inspection.

The native stored descriptor bytes are `0c040000` for French and `09040000` for
General Legacy. Actual ascending orders for the four accent probes are:

| Stored order | ID order | Text order |
| --- | --- | --- |
| French 1036/0/0 | 3, 5, 4, 6 | cote, côte, coté, côté |
| General Legacy 1033/0/0 | 3, 4, 5, 6 | cote, coté, côte, côté |

Descending reverses those four distinct-key orders. Full French keys include
`7f4d646d51010e00` for `coté` and `7f4d646d510102021200` for `côte`;
the corresponding General keys are `7f4d646d51010202020e00` and
`7f4d646d5101021200`. These are observed bytes, not generated by TableCraft.
Complete equal-key row references remain available to specify tie order.

Other inputs cover NULL, empty, identical and case ties, trailing spaces,
composed/decomposed accents, apostrophe/hyphen/space/punctuation, œ/oe, æ/ae,
ß/ss, embedded NUL, non-BMP text and 255-unit values. Nonunique complete keys
reaching the 510-byte entry ceiling are observed. Unique overflow remains an
explicit separate negative, not a capability admitted by these originals.

Microsoft's [sorting guidance](https://learn.microsoft.com/en-us/globalization/locale/sorting-and-string-comparison#characters-with-diacritics)
describes backward secondary sorting in some French dictionary traditions.
That general linguistic guidance explains the discriminator; it does not specify
ACE descriptor bytes, its key format, a native NLS version or Access SQL behavior.
The exact persisted-key evidence here comes from the pinned independent writer
and raw bytes. No ICU substitution or copied upstream weights/code is introduced.

## Boundaries and reproduction

ignore-NULL, relationship or mutation profiles. Persisted index encoding/checks
and full-string comparison-provider admission require separate implementation
and acceptance. Index prefix truncation/digests cannot supply arbitrary SQL
comparison. LIKE, search and automatic equality-prefix selection are also
separate; no General-family recognition is broadened by these observations.

The initial Java compile failed because `setTextSortOrder` returns void and was
incorrectly chained. The correction calls it separately. The original source and
a contemporaneous diagnostic summary are retained and hash-pinned; the summary
is not represented as a raw compiler log. Generation had not run at that failure,
and no accepted original was regenerated or patched afterward.
