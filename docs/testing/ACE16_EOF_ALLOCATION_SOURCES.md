# First EOF DATA allocation sources

Two authored BEFORE files retain the original genuine database length and all
map bytes, but fill the existing Sentinel root directory with inert deleted
entries. The next page at the true original EOF is independently checked as
represented GLOBAL-free, unowned and absent from the candidate map.

The [literal model](owned_growth_originals/eof_model.py) and
[original requests](owned_growth_originals/eof_requests.json) predict a single
4096-byte DATA append. The new hidden record and forwarding capsule retain the
logical root. Exactly three original map bits change; the saturated root's
candidate hint and every other original byte remain protected. No existing
writer or alternate-page output constructs the expectation.

To reconstruct a profile from its pinned original and original SDK report, call
`source(original, profile)`, then
`construct(original, before, original_report, profile)`. The latter returns the
complete AFTER, raw proof and predicted reader report. Original provenance and
all artifact hashes are in the [source record](results/ace16-eof-allocation-sources-2026-11-01.json).
Retain generated files outside Git and use copies for later mutation experiments.

The ignored native gate
`normal_ordinary_sources::eof_allocation::genuine_eof_allocation_sources_and_literal_after_read_before_any_writer`
reads four views under explicit
`TABLECRAFT_PROPERTY_LVAL_ORIGINALS_DIR` and
`TABLECRAFT_EOF_ALLOCATION_EXPECTED_DIR` directories. All four also match complete
independent SDK reports, with inputs unchanged. These source checks call no
allocation producer or stored program.

Normal allocation, V2 native-intent recovery and resized retained-session saves
remain separate implementation work. Independent source reads do not establish
Microsoft Access allocation choices or native save/reopen compatibility.
