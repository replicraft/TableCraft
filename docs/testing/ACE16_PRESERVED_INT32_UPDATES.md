# Preserved mixed-schema Int32 engineering updates

The existing fixed/batch engineering services gain a separate closed path for one
ordinary, nonindexed, calculation-independent Int32 target in a qualified mixed
schema. Requests must supply exact non-NULL Int32 expected/new values. This creates
an `Ace16WritePreview`, not a normal edit plan or journal/save permission. Existing
Boolean-only requests retain their prior staging/proof bodies and charged costs.

## Source and original authority

The path reuses the existing preserved source certification: native origins,
GUIDs/names/qualified properties, calculated dependencies, attachments and opaque
nullable payloads, complete records, physical INDEX owners, LVAL ownership and
GLOBAL/map allocation. Participating relationships remain refused. Required and
validation checks still apply. `PublishToWeb=1` remains unqualified/refused; this
feature does not establish donated-file editing support.

Only one Int32 column group is admitted. Boolean/numeric mixtures, NULL carriers,
indexed/generated/calculated/dependent targets and other field representations
remain outside this new path. Original field metadata and original requests select
and validate the numeric profile. An empty numeric request may enter only after
exact metadata qualification of an ordinary fixed Int32; no staging, resource,
conflict or cancellation failure triggers an alternate writer.

Staging emits only the original four-byte field span, retaining the native NULL
mask and fixed-area padding. A separate proof recaptures source facts and rebuilds
expected bytes from original requests and records. It rejects an alternative
valid candidate made from a different request, unrelated byte changes and an
incorrect changed-row count. Candidate source certification runs again afterward.

## Independent authored corpus

The actual rich Boolean source builder is reused without modifying its bodies.
Its original Int32 columns ID and Number are indexed and calculation-dependent.
A separate authored original therefore declares the existing unindexed field
`Large_Number` as Int32 with width 4 at its existing fixed offset 8, instead of its old
Int64 with width 8. The former upper four bytes remain untouched padding. Its label does
not determine its type. All GUIDs, names, properties, indexes, calculations,
attachments, LVAL storage, masks and opaque bytes remain retained.

Eight complete original/expected pairs cover headers 5 and 6, with replacements
101, -101, 2147483647 and -2147483648 for row 0's original value 1000. Expected images change exactly
the literal four-byte field. In particular, negative replacements must not
sign-extend into the former upper word. There are four supported code 6 originals.
The four code 5 originals retain Extended Date declarations whose scalar metadata
is unsupported under that header and are preservation-refusal controls.

The first SOURCE gate passed eight pairs and sixteen selected scalar/advanced views and
role checks. Before any producer ran, static review identified that those selected reads did not imply
complete code 5 preservation admission. A stronger SOURCE gate explicitly checked
both native type 20 fields and confirmed their profile-dependent scalar availability.
All original model and expected bytes stayed unchanged. This is a source
qualification correction, not a writer repair or header retargeting.
